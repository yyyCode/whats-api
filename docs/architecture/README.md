# 架构分析文档集

这是一套针对 **New API**（Go 编写的 AI 网关与资产管理平台）的架构分析，目的不是复述代码，而是**提炼出可复用的设计决策**，供后续自建类似平台时参考。

- 分析对象：本仓库当前源码树（后端约 1033 个 Go 文件，前端约 1386 个文件）
- 目标技术栈假设：Go + Gin + GORM + React（文档中的代码骨架可直接对应到这些技术）
- 文章写法：**问题是什么 → 关键抽象 → 核心代码 → 自建时的取舍与坑**

## 十条核心设计思想

如果只能带走十句话：

1. **协议转换是纯函数，应独立成模块；计费有副作用，必须留在宿主。**
2. **转换永远成功，丢掉了什么如实报告；只在可逆的地方（请求前）允许失败。**
3. **请求上下文必须区分"跨尝试共享"与"每次尝试重置"——这是重试安全的全部秘密。**
4. **不要缓存"选中结果"，只缓存"候选集"；"命中缓存"和"负载均衡"是两件事。**
5. **把查询的结果预先存下来（反范式索引表），而不是优化查询本身。**
6. **金额只用整数；数值溢出的三档语义（Strict / Checked / 基础）；异常必须留痕。**
7. **并发安全的本质是"原子的检查并扣减"（条件 UPDATE / Lua），不是加锁顺序。**
8. **跨时间的业务必须存计价快照；跨时间的计费不能按当前配置算。**
9. **配置系统用"结构体 + tag + 注册"生成 schema/默认值/key/文档，避免五份定义漂移。**
10. **分布式锁不只要能加，还要能在失去锁时停止工作。**

再加三条"什么时候不做"：

- 稳定扩展点用 switch（编译期检查、可读），只有需要热更新的扩展点才上插件系统；
- 先穷尽配置（映射 / 覆盖 / 选项），再考虑写代码；
- **本项目的复杂度是业务长出来的，照抄终态会得到一个你无法维护的系统。**
